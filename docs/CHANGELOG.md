# 变更记录（近期）

## 2026-11-13 1.0.1：卡帧 / 幻灯片排查与修复

全库扫了 1048 个视频（/stream/list），按编码、分辨率、位深、码率、帧率、隔行标记分类：

- **高码率直连卡顿**：电影库大量 1080p 蓝光 remux，码率 25–38 Mbps（《警察故事4》36M、《醉拳》38M）。
  走系统播放器原画直连时电视 WiFi 吃不下 → 卡住/幻灯片。规则改为 **源码率 > 20 Mbps 一律服务器转码**（1080P/12–14 Mbps）。
- **1080i 隔行片源**（《霹雳火》）：直连不做反交错，画面会花/卡。规则改为 **progressive=0 转码**。
- **4K HEVC + MP4**（动画电影里很多）：沿用上一版规则强制转码。
- **4K 片源整体改为转码**：电视面板就是 1920×1080，4K 原画不会更清晰，
  却要老 MTK 硬解 + WiFi 扛 4K 码流（4K H.264 MP4、4K HEVC MKV 共 31 个），全部转 1080P 更稳。
- **10bit / DTS / TrueHD**：继续转码。
- 新增**卡帧看门狗**：播放中位置连续 8 秒不动，自动换 VLC 重新起播一次（只做一次，避免反复重启）。
- 修正码率读取：服务端字段名是 `bps`，之前只读 `bit_rate`/`bitrate` 导致码率恒为 0、规则不生效
  （实测《警察故事4：简单任务》36 Mbps 仍走原画直连 → 准备超时）。
- 结果：1048 个条目里 556 个转码、492 个直连（直连的都是 ≤20 Mbps 的 H.264 / 4K HEVC MKV）。

**4K HEVC + MP4 能不能不转码？——结论：这台电视上不行**

实测三条路都不通：

1. **MediaCodec 直解 HEVC**（ExoPlayer 走的也是这条）：`OMX.MTK.VIDEO.DECODER.HEVC`
   configure 4K/1080p 都成功，但喂真实码流（csd-0 / codec-config / 首帧带 VPS-SPS-PPS 三种方式都试过）
   **一帧都解不出来**；同一条代码路径解 H.264 正常。说明 MTK 这颗 HEVC 解码器只服务于自家
   CmpbPlayer，Android MediaCodec 通道拿不到输出。
2. **系统播放器直连 4K HEVC MP4**：MTK 固件解析 hvc1 时把整机拖进看门狗 → 重启（《安全警长啦咘啦哆》）。
   同内容换成 MKV（《宁安如梦》）就完全正常，所以是容器相关，不是编码本身。
3. **转码成 4K H.264**（/play/play resolution=2160）：服务器能出流，但 App 侧 VLC 在 4.4 上是软解，
   4K H.264 直接 `more than 5 seconds of late video -> dropping frame`，无法观看。

因此这类片子保持 **1080P H.264 转码**（当前行为）。
如果想让它们 4K 原画播放，只剩一个办法：在 NAS 侧把这些 4K HEVC 的 **MP4 重新封成 MKV**
（ffmpeg `-c copy`，几十秒一个文件），App 这边对 MKV 是原画直连的。

## 2026-11-01 修复「播《安全警长啦咘啦哆》立即重启电视」

**根因（已定位）**：这部剧是 **4K HEVC（hvc1）+ MP4 容器**（3840×2160 / 25fps / 8bit / AAC）。
这台 MTK 电视的系统播放器一接到「4K HEVC 的 MP4 直连流」就会把整机拖进看门狗重启
（早期用官方 4K HEVC MP4 测试片时，自带播放器也是直接弹「无法打开该文件」）。
对照实验：4K HEVC 的 **MKV**（《宁安如梦》）正常播放 10 分钟以上；
4K **H.264** MP4（《长安三万里》）也正常 —— 只有 HEVC + MP4 + 4K 这个组合会崩。

**修复**：转码策略里增加一条硬规则 ——
`HEVC + MP4/MOV + 分辨率 ≥ 1440p → 一律服务器转码（1080P H.264，走 VLC）`。
其它组合维持原样（4K HEVC MKV 仍原画直连、4K H.264 仍原画直连）。

**实测**：《安全警长啦咘啦哆》第 1 集现在走「转码 · HLS」，
画面正常、声音正常，连续播放 2 分钟以上，电视 uptime 没有中断（没有再重启）。

## 2026-11-01 4K 原画直连（系统播放器重新接入，实测可用）

**起因**：查到电视剧《宁安如梦》是 4K HEVC（3840×1608, 8bit, EAC3 5.1）。
重新验证后确认：之前判定的「系统播放器黑屏」是**误判** —— MTK 把视频放在独立视频层，
`adb screencap` 抓不到视频内容（只拍到 UI/黑底），但电视屏幕上画面是正常的。
用一条红色横幅叠加测试也确认：App 自己的 UI（HUD/控件）能正常压在视频层之上。

**改动**

- 新增 `player/SystemPlayerEngine`：`MediaPlayer`（MTK CmpbPlayer）直连播放，用于原画直连。
- `NativeVideoPlayerView` 引擎选择：
  - 原画直连（http 直链、非 HLS）且格式系统能解 → **系统硬解**；
  - 转码 HLS（`file://` m3u8）、RMVB/AVI/FLV 等、设置里关掉硬解 → **VLC**；
  - 系统播放器报错 → 本片自动换 VLC（保留硬解尝试）；
  - 系统播放器 10 秒没出首帧 → 自动换 VLC；
  - 倍速播放时（4.4 的 MediaPlayer 不支持变速）自动切到 VLC 再变速。
- `FnosRestClient` 转码策略放宽：
  - HEVC / H.264 都不再因为「非 H.264」或「4K」强制转码；
  - 音轨：DTS / TrueHD 仍然转码，AC3/EAC3/DDP ≤6 声道直接播（实测 EAC3 5.1 有声）；
  - 视频位深 >8bit（10bit/HDR）暂仍转码，等实测通过再放开。
- 播放器状态标签在系统播放器下显示「MTK 硬解 · 原画直连」，不再显示 VLC 的缓存参数。

## 2026-11-01 4K / H.265 10bit 解码能力实测（调试工具，发布版已移除）

> 下面这段是内部排障记录：`CodecProbeActivity` / `Mp4Probe` 已在 1.0.0 发布版中删除。

新增开发者工具（不在桌面/主界面暴露入口，用 adb 启动）：

```
adb shell am start -n com.fnostv.android4/.CodecProbeActivity \
  --es path /sdcard/Movies/xxx.mp4 [--es play 1]
```

- `CodecProbeActivity`：列出 `video/hevc`、`video/avc` 解码器与 profile，自己解析 MP4（`Mp4Probe`）
  取 `hvcC` / `avcC`，直接 configure MediaCodec，并喂前 120 帧统计出帧数；`--es play 1` 时用 App 的 VLC 引擎放同一文件。
- 实测结论（AQUOS 60UD30A / mt5861 / Android 4.4.3）：
  - 硬解器存在：`OMX.MTK.VIDEO.DECODER.HEVC`、`OMX.MTK.VIDEO.DECODER.AVC`；
  - `OMX.MTK.VIDEO.DECODER.HEVC` **接受** 3840×2160 / HEVC Main10 / level 5.1 的 configure（不报错，
    说明芯片侧宣称支持 4K 10bit）；
  - 但 Android 4.4 的 `MediaExtractor` **不认识 HEVC 轨道**（hvc1 MP4 被识别成
    `application/octet-stream`），所以任何走系统解封装的原画 HEVC 播放都拿不到码流；
  - App 内 VLC 在这台机器上是**软解**：4K HEVC 日志刷 `more than 5 seconds of late video -> dropping frame`，
    1080p H.265 正常；
  - 电视自带播放器（MTK CmpbPlayer）：1080p HEVC 10bit 能起播（`MEDIA_INFO_VIDEO_RENDERING_START`），
    但 4K HEVC（40Mbps / 60fps，8bit 与 HDR10 10bit 均测）直接弹「无法打开该文件！」
    （`start() wait for started` 超时）。
- 因此：**App 里 4K H.265 原画目前放不了**，继续按现有策略转码（1080p / H.264 / 12Mbps）最稳。
  若以后要试 4K 原画，下一步是 ExoPlayer 2.18.1（自带 MP4 解封装 + MediaCodec + Surface），并优先用 4K30 片源验证。

## 2026-11-01 尝试系统硬解引擎（已回退）

- 新增 `SystemPlayerEngine`（MediaPlayer → MediaCodec/OMX），只用于原画直连，转码流/特殊格式仍走 VLC。
- 实测（MTK5861 / Android 4.4）：MediaPlayer 确实调起了 MTK 硬解（日志 `Display Video in Abs Rect 1920x1080`），
  但画面全黑——MTK 的视频层没有合成到 App 的 SurfaceView 上；6 秒无画面自动回退 VLC 也验证过。
- 结论：这台电视上用系统播放器不可行，已回退成 VLC 单引擎（VLC 开硬解时同样走 IOMX 硬解），
  避免用户遇到黑屏。若以后要继续硬解路线，建议上 ExoPlayer（自带 Surface 处理）。

## 2026-10-31 播放卡顿 / 画面乱码修复

- **画面乱码**：VLC 默认参数里一直带着 `:avcodec-skiploopfilter=48`（跳过去块滤波），
  这是早年为了省 CPU 加的，高码率 H.264 上会一块一块的。现在只在「流畅模式」启用，
  正常播放保留去块滤波。
- **一卡一卡**：默认参数里带着 `:no-drop-late-frames` + `:no-skip-frames`（永不丢帧），
  解码稍慢就会卡；现在默认允许丢帧保持音画同步，只有流畅模式才禁止。
- **HLS 缓冲**：网络缓存上限 3s → 6s（分片 4s，WiFi 抖动时 3s 会周期性卡顿）。
- **转码码率上限** 20Mbps → 14Mbps，降低老盒子的解码/网络压力。
- **HLS 列表文件改为每次新建文件名**（并只保留最近 4 个）：拖动刷新列表时不再覆盖

## 2026-10-30 登录被拒（131072）兜底

- 现象：别人家的 fnOS 登录时报「请求失败，131072」，进不了 App。
- 原因：这是 **fnOS 服务端拒绝 RPC（WebSocket）登录** 返回的错误码，不是地址/密码问题；
  常见于服务端版本与 RPC 登录协议不一致，或账号开启了两步验证/登录保护。
- 处理：RPC 登录被拒时自动回退到**网页同款 REST 登录**（`/v2/login` + sha256 密码），
  媒体库、播放、收藏都走 REST，所以 REST 能登就能正常使用。
- 若 REST 也被拒，登录页会把 131072 翻译成可执行提示（关闭二次验证 / 用应用密码 / 核对 fnOS 版本）。

## 2026-10-29 转码流拖动（落地版）

抓包确认：网页播放器拖动时只请求对应 `.ts` 分片（拖到 20:00 请求 00299.ts），
前提是服务器已经转好那一段；App 之前本地只有开播那一刻的列表快照，所以跳不远。

现在的行为：

1. 拖动 > 15 秒：重新拉取同一会话的 HLS 列表（覆盖本地缓存）
2. 用新列表重建播放器，**首帧出来后再 seek**（VLC 在 onPrepared 里立刻 setTime 会被丢掉，
   这就是「跳完归 0」的直接原因），0.9 秒后校验，没到位再补 seek
3. 目标超出服务器已转码范围：先跳到最远可播位置并提示「已跳到最远可播位置 mm:ss」；
   如果落点离目标太远、又没跳成，则退回原位置并提示「该位置还在转码，请稍后再拖」，
   不会再出现停在片头/归零
4. 连续按键只处理最后一次目标

实测 4K《宁安如梦》：开播十几秒后按 20%（8:20）→ 落点 08:19；按 80%（33:20）时
服务器只转 ~29 分钟 → 落在 29:09 并有提示。

## 2026-10-29 转码流拖动（最终方案）

- 抓网页版播放器确认：它拖动时只请求对应的 `.ts` 分片，不做服务端 seek；
  前提是服务器的转码列表已经覆盖到那个位置。
- App 的根因：本地缓存的是开播那一刻的 HLS 列表快照，VLC 又按 VOD 只读一次。
- 现在的做法：
  1. 拖动超过 15 秒 → 重新拉取同一会话的 HLS 列表（覆盖本地缓存）；
  2. 用新列表重建播放器，跳到目标；
  3. 列表里能算出「服务器已转码到哪」（EXTINF 总和），目标超出时先跳到最远可播位置，
     并提示「该位置还在转码，已跳到 mm:ss」；转码追上后再跳就准了。
- 实测（4K 剧集）：开播约 2 分钟后按 20%（8:20）→ 落在 8:29（含 +10 秒），准确；
  开播初期目标超出转码进度时会落到当前转码头并提示，不再出现「从头播放」的错觉。

## 2026-10-29 转码流拖动（抓包后的正解）

- 抓网页版播放器实测：4K 剧集拖到 20:00 时，网页直接请求 `00299.ts`（4 秒一片），
  说明**服务器的转码列表已经覆盖到 20 分钟**（约 8 倍速转码），网页本身并不做服务端 seek。
- 根因确认：App 本地缓存的是「开播那一刻」的 HLS 列表快照，VLC 又按 VOD 一次性读入，
  所以只能在快照范围内跳；超出就落到末尾（画面/时间错位，看着像从头播）。
- 修复：拖动超过 15 秒时，先重新拉取同一会话的 HLS 列表覆盖本地缓存，
  再用新列表重建播放器并跳到目标；如果列表还没转到位，每 1.2 秒重试，最多 6 次。
- 连续按键合并成最后一次目标，重试期间也只保留最新目标，不会叠加重启。

## 2026-10-28 快进/快退排查结论（转码流）

- 已修：连续快进/快退的累加基准、跳转后等待与补 seek、时间归零兜底、总时长被缩短。
- 排查结论（实测 4K/HEVC 剧集）：
  - 服务器 /play/play 返回的是**从 0 开始的 VOD 列表**，startTimestamp 无论传秒还是毫秒都被忽略；
  - 我们本地缓存的是**播放开始那一刻的列表快照**，而服务器是边转边出片；
  - 因此「向前大幅跳」只能落到快照末尾，表现为画面/时间对不上、甚至像从头开始。
- 试过两条修复路线都回退了：重新请求带 startTimestamp 的会话（服务器忽略）、定期刷新列表（转码速度跟不上），
  都会引入卡死/时间翻倍，故不保留。

## 2026-10-28 快进/快退准确性

  连按会越跳越偏）。
- 跳转后等待时间从 2.4s 延长到 6s，并在中途补发一次 seek（HLS 重新起流后 VLC 常把时间归零，
  补一次能拉回来）。
